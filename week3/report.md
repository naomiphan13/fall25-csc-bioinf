In Codon the biggest theme was strict, ahead-of-time typing. I had to keep object types consistent across modules and avoid annotating Python interop objects with NumPy-style generics (e.g., np.ndarray[int,2]), because anything imported via from python import ... is a pyobj and Codon will try to subscript a Python class at compile time. When values can be missing, I explicitly used Optional[...] and guarded every use; otherwise Codon tries to auto-unwrap and you get the classic “optional unpack failed” error. For example, this came up in tree utilities where parent chains or LCAs could be None, so I added Optional[TreeNode] for the "node" parameter in lowest_common_ancestors() method.

Codon doesn’t support @classmethod constructors; instead I used multiple __init__ overloads with @overload and made sure every path initializes all fields (_parent, _children, _distance, etc.). As Codon doesn't support np.float32, I changed all to np.float64 instead. I also learned that small int/float mismatches (like passing 0 instead of 0.0 for a branch length) can cascade into constructor checks or subtle numeric diffs.

File paths behaved differently on CI because relative paths depend on the current working directory. Locally I was running from a folder where ../data happened to point at the right place; CI didn’t. I fixed this by by cd-ing to the script directory in the shell, which removed the environment-sensitivity and stopped the “file … could not be opened” errors.

Because np.loadtxt wasn’t reliable under Codon in my setup, I rewrote the distances() loader using plain file I/O and float(...) parsing; this also let me support both comma- and space-separated input lines. For testing, pytest isn’t available by default in Codon, so I replaced pytest.approx with a Codon-safe numerical comparison that combines absolute and tiny relative tolerances (e.g., abs(a-b) <= max(1e-3, 1e-12*max(|a|,|b|))), which matches the intent without pulling in pytest.
